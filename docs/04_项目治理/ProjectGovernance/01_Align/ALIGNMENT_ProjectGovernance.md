# 项目治理任务对齐文档 (ALIGNMENT)

## 1. 任务背景与目标
用户希望能对现有分散的功能和文档进行治理，建立过程管理，输出分层级（L1-L3）的整体项目文档，并确保代码、文档、测试的一致性与可用性。

## 2. 原始需求分析
1.  **整理需求文档**：针对 `docs/` 目录下的文档进行梳理。
2.  **输出整体项目文档**：按 L1（用户级）、L2（业务逻辑/维护级）、L3（代码实现级）分层输出。
3.  **代码与文档双向同步**：检查代码是否符合文档描述，文档是否反映最新代码。
4.  **检查测试系统**：评估现有测试系统的满足度（发现 `test` 和 `tests` 两个目录并存的冗余情况）。
5.  **运行全量测试**：确保治理后的系统功能正常。

## 3. 现状分析
*   **文档结构**：目前 `docs` 下已有 `01_核心系统`, `02_功能模块`, `03_维护与修复` 的良好分类，但可能存在碎片化问题。
*   **代码结构**：核心代码在 `src/`，Web端 in `web/`，脚本 in `scripts/`。
*   **测试结构**：存在 `test/` (主要，包含 unit, integration, ui, bats) 和 `tests/` (疑似遗留) 两个目录，`pytest.ini` 指向 `test/`。
*   **技术栈**：Python (Core/Web), Shell (Modules), Bats (Shell Testing), Pytest (Python Testing).

## 4. 治理策略与决策
1.  **文档治理**：
    *   保持 `docs/01...03` 的物理结构作为"源码/单一事实来源"。
    *   创建一个新的汇总文档 `docs/Project_Unified_Manual_L1_L3.md`，通过引用或整合现有文档内容生成。
    *   L1: 提取各模块的 `FINAL_*.md` 或 `Readme.md` 中的用户指南部分。
    *   L2: 提取 `DESIGN_*.md` 中的架构和流程图。
    *   L3: 提取 `TASK_*.md` 或直接根据代码生成的 API/类定义。
2.  **测试治理**：
    *   **决策**：合并 `tests/` 到 `test/`，消除歧义。将 `tests/*.py` 迁移至 `test/unit/` 或 `test/integration/` 下的合适位置。
    *   确保所有测试均可通过 `pytest` 运行。
3.  **代码同步**：
    *   通过运行测试覆盖率 (`pytest --cov`) 发现未测试/文档未覆盖的代码。
    *   人工抽检核心模块 (`src/core`) 的文档一致性。

## 5. 疑问与澄清
*   **Q**: `tests/` 目录下的测试是否仍有效？
    *   **A**: 假设有效，迁移时运行验证，无效则修复或归档。
*   **Q**: L1-L3 是一个大文档还是三个？
    *   **A**: 用户要求"一份整体的项目文档...逐层输出"，建议合并为一个文档，使用一级标题区分层级，方便检索。

## 6. 验收标准
1.  `docs/` 目录结构清晰，无明显冗余。
2.  产出 `Project_Unified_Manual_L1_L3.md`，包含用户指南、系统架构、代码规范/API。
3.  `tests/` 目录被移除，所有有效测试迁移至 `test/`。
4.  `pytest` 全量通过。
5.  代码与文档的关键差异被修正。
