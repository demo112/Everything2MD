# ALIGNMENT: LLM Markdown Cleaning (解析增强 - 结构化清洗)

## 1. 项目上下文分析

Everything2MD 目前已具备多格式转 Markdown 的能力，并正在构建 "解析增强" (Parsing Enhancement) 模块，目前主要包含 "图片识别" (Image Recognition) 功能。
- **现有架构**:
  - `src/gui/main.py`: 包含 "解析增强" 页签。
  - `src/core/engine.py`: 转换引擎，支持管道式处理。
  - `src/core/image_recognition.py`: 现有的增强模块。
  - `src/core/config.py`: 统一配置管理。

## 2. 需求理解

**原始需求**:
- 在 "解析增强" 模块下增加新子模块。
- 配置 LLM 对转换后的 Markdown 文件进行 "格式清洗"。
- 目标: 实现转化后 MD 文档的结构化可靠与优化。
- **核心约束**: **内容绝对不能被改写，哪怕是一个字符的偏差都不能接受**。风险极高，必须严格控制。

**需求拆解**:
1.  **UI 变更**:
    - 在 "解析增强" 页签中，增加 "结构化清洗" (Structure Cleaning) 的相关配置。
    - 开关 (Enable/Disable)。
    - LLM 配置 (可能与图片识别共用，也可能独立，需确认)。
2.  **核心逻辑**:
    - 读取 Markdown 文件。
    - 构建 Prompt，要求 LLM 仅调整 Markdown 标记 (Headers, Lists, Tables)，保持文本内容原样。
    - 流式或一次性接收 LLM 响应。
    - 写入新文件或覆盖原文件。
3.  **安全与验证**:
    - 必须有机制验证内容未被篡改。
    - 比如: 提取纯文本 (去除 Markdown 标记) 进行对比? 或者计算纯文本 Hash?

## 3. 疑问与澄清 (智能决策)

### Q1: LLM 配置策略?
- **选项 A**: 复用 "图片识别" 的 LLM 配置 (Base URL, API Key)。
- **选项 B**: 独立配置。
- **决策**: 考虑到 "图片识别" 通常需要 Vision 模型 (如 gpt-4-vision)，而 "结构化清洗" 只需要强大的文本模型 (如 gpt-4o/deepseek-chat)，且两者 Token 消耗和计费可能不同。
- **建议**: **允许独立配置，但提供"使用通用配置"的快捷方式**。为简化实现，初期可以在 GUI 上增加一套新的 Model/API Key 输入框，或者复用 Base URL/Key 但允许指定不同 Model。
- **本次策略**: 为了灵活性，在 GUI "解析增强" 页签下，将配置区域分为 "通用/基础配置" (Base URL, Key) 和 "功能特定配置" (图片识别模型 vs 清洗模型)。或者简单点，增加一组独立的配置区给清洗功能。考虑到 GUI 空间，**复用连接信息 (URL/Key)，但区分 Model** 是比较合理的。但如果用户想用不同的服务商（比如图片用 OpenAI，清洗用本地模型），则需要完全独立。
- **最终决策**: **完全独立的配置区** (Base URL, Key, Model)，因为用户极可能使用不同的模型服务（例如用便宜的 DeepSeek 做清洗，昂贵的 GPT-4V 做识图）。

### Q2: 如何保证 "一个字符都不能改"?
- **挑战**: LLM 本质是概率模型，很难保证 100% 逐字输出。
- **策略**:
    1.  **Prompt 强约束**: "You are a Markdown formatter. Do NOT change any text content. Only fix headers, lists, and spacing."
    2.  **后置验证 (关键)**:
        - 在写入结果前，将 *原 MD* 和 *新 MD* 都剥离所有 Markdown 标记 (只保留纯文本)。
        - 对比纯文本是否一致 (通过 Hash 或 Diff)。
        - **如果验证失败**: 丢弃 LLM 结果，保留原文件，并记录错误日志。这是唯一能满足 "哪怕一个字符都不能接受" 的兜底方案。

### Q3: "结构化清洗" 具体指什么?
- **理解**:
    - 修复错误的层级 (如 `#` 没空格)。
    - 修复列表断裂。
    - 修复表格格式。
    - 移除冗余空行。
    - 规范化代码块。

## 4. 风险评估
- **幻觉风险**: LLM 可能会"脑补"内容。 -> **对策**: 纯文本一致性校验。
- **截断风险**: 长文档可能超过 Context Window。 -> **对策**: 分块处理（极难保证边界结构）或仅支持长窗口模型 (128k+)。鉴于 "Everything2MD" 可能处理大文件，**分块处理** 是必须考虑的，但分块处理结构化清洗非常困难（跨块标题/列表）。
- **简化策略**: 既然是 "优化"，如果文件太长，可以跳过或报错。或者明确限制支持的文件大小。考虑到 LLM 成本和速度，初期版本建议 **不做切分**，直接利用长窗口模型，若超过 Token 限制则跳过并报警。

## 5. 验收标准
1.  GUI 增加 "结构化清洗" 配置区。
2.  转换流程中，若开启该功能，在转换完成后调用清洗逻辑。
3.  **核心**: 经过清洗的文档，纯文本内容与原文档 **完全一致** (Hash 校验)。如果不一致，回滚并报错。
4.  测试用例覆盖: 包含乱序结构的 MD，验证清洗后结构正常且内容不变。
