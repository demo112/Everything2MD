# CONSENSUS: 版本管理规范与历史记录

## 1. 最终共识
经过对项目历史的梳理和未来发展的规划，我们达成以下共识：

### 1.1 版本历史追溯
我们将基于 Git 提交时间轴和功能特性，人为划分历史版本，以建立清晰的演进脉络。
- **v0.7.0** (2025-12-16): 核心模块测试覆盖率提升，打包配置优化，构建产物清理。
- **v0.6.0** (2025-12-15): 引入 RAGFlow 集成，增强测试体系。
- **v0.5.0** (2025-11-28): 新增 Docker 部署支持，重构项目文档结构。
- **v0.4.0** (2025-11-27): Tkinter GUI 界面功能优化。
- **v0.3.0** (2025-11-13): Windows 原生 EXE 支持，集成 BusyBox，CI/CD 工作流优化。
- **v0.2.0** (2025-11-11): 初始 GUI 支持，引入 Bats 测试框架，PPT 处理修复。
- **v0.1.0** (2025-11-10): 项目初始化，核心文档转换功能实现。

### 1.2 版本号管理策略
采用 **Semantic Versioning 2.0.0** (SemVer)。
- **主版本号 (Major)**: 0 -> 1 (当 API 不兼容或正式发布稳定版时)。目前保持在 0.x.x 阶段。
- **次版本号 (Minor)**: 引入新功能 (feat)。
- **修订号 (Patch)**: Bug 修复 (fix) 或构建/文档调整 (chore/docs)。

### 1.3 更新日志生成要求
- 维护根目录下的 `CHANGELOG.md` 文件。
- 遵循 **Keep a Changelog** 格式。
- 每次发布新版本前，需将 `Unreleased` 部分归档为具体的版本号。

### 1.4 代码提交规范
强制执行 **Conventional Commits**。
- `feat`: 新功能
- `fix`: Bug 修复
- `docs`: 文档
- `style`: 格式
- `refactor`: 重构
- `test`: 测试
- `chore`: 构建/工具

## 2. 技术实现方案
- **手动维护为主，脚本辅助为辅**：目前不需要引入 husky 或 commitlint 强制拦截（避免环境依赖过重），但通过文档规范约束开发人员。
- **Changelog 生成**：首次由 AI 根据 git log 生成完整历史，后续由开发者手动追加或使用脚本辅助提取 git log 待编辑。

## 3. 验收标准
1. 项目根目录存在 `CHANGELOG.md`，包含从 v0.1.0 到 v0.7.0 的完整记录。
2. 项目文档（如 `README.md` 或 `CONTRIBUTING.md`）中包含版本管理和提交规范的说明。
3. 规范文档清晰易读，无歧义。
