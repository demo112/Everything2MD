# ALIGNMENT_配置系统重构

## 1. 项目上下文分析
当前 `Everything2MD` 项目使用 `ConfigParser` 管理 `config.ini` 配置文件。
原有的配置管理方式存在以下问题：
1. **分散的逻辑**：配置键值的读取和写入分散在 `ConfigManager` 的 `get` 和 `set` 方法中，包含大量 `if/else` 判断，难以维护。
2. **手动绑定**：GUI 层的变量与配置项之间的同步需要手动编写代码，容易遗漏（如本次发生的结构化配置未持久化问题）。
3. **扩展性差**：每增加一个新配置项，需要在多个地方（ConfigManager 映射、GUI 初始化、GUI 加载、GUI 保存）修改代码。

## 2. 需求理解确认

### 2.1 原始需求
- **修复 Bug**：文档结构化的相关配置没有持久化。
- **预防复发**：通过架构改进，防止未来再次出现配置未保存的问题。

### 2.2 核心目标
- **配置映射中心化**：在 `ConfigManager` 中建立统一的“配置键 -> (Section, Option)”映射表，消除魔术字符串和冗余判断。
- **GUI 绑定自动化**：在 GUI 中建立“配置键 -> Tkinter 变量”的绑定关系，实现通用的 `load_config` 和 `save_config` 方法。
- **零手动同步**：新增配置项只需在映射表和绑定表中注册，无需修改加载/保存逻辑。

### 2.3 边界确认
- **范围**：仅重构 `src/core/config.py` 和 `src/gui/main.py` 中与配置读写相关的逻辑。
- **不包含**：不改变配置文件的格式（仍为 INI），不改变现有的配置项名称（保持兼容）。

## 3. 智能决策策略

### 3.1 关键决策
- **决策 1**：保留 `ConfigManager` 的 `get/set` 接口签名，内部实现改为查表法。这样可以兼容项目中其他调用 `ConfigManager` 的代码。
- **决策 2**：在 GUI 类中引入 `_init_config_bindings` 方法，显式定义配置项与 UI 组件的对应关系。
- **决策 3**：保留类型转换逻辑（如将 "true"/"false" 字符串转换为 boolean），以兼容 shell 脚本对配置文件的读写习惯。

## 4. 疑问与澄清
- **Q1**: 是否需要迁移旧的配置文件？
  - **A**: 不需要。新的逻辑兼容旧的 INI 结构。
- **Q2**: 特殊配置（如 `soffice_path` 的自动检测）如何处理？
  - **A**: 自动检测逻辑保留在 GUI 初始化或加载流程中，检测结果更新到绑定的变量中。

## 5. 最终共识
我们将实施基于映射表的配置管理方案，消除硬编码，实现 GUI 与配置系统的自动化同步。
