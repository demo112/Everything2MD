# ALIGNMENT: 大文件自动切分策略

## 1. 项目上下文分析

### 1.1 现有架构
Everything2MD 的核心功能是将各类文档转换为 Markdown。
- **转换引擎**: `src/core/engine.py` 负责调度转换流程。
- **输出处理**: 目前转换后的 Markdown 文件通常作为一个单一文件输出。
- **配置管理**: `src/core/config.py` 管理应用配置。

### 1.2 现有痛点
当处理超大文档（如几百页的 PDF 或 PPT 转换后的 Markdown）时，生成的单个 Markdown 文件可能体积过大（例如超过 100MB），导致：
- 编辑器打开缓慢或崩溃。
- LLM 上下文窗口限制无法一次性处理。
- 阅读和检索困难。

## 2. 需求理解与确认

### 2.1 原始需求
> "补充一个策略，设置一个输出文档体积阈值，超过该阈值的文档，需要被均分为若干个小于该阈值10%的文档。比如一个文档100M，阈值是50m，那么在转化时就要转化为3份 33m的文档。"

### 2.2 需求拆解
1.  **配置项**: 新增 `MAX_OUTPUT_SIZE` (或其他命名) 配置项，单位为 MB。
2.  **触发条件**: 生成的 Markdown 文件大小 > `MAX_OUTPUT_SIZE`。
3.  **切分逻辑**:
    - 目标单文件大小 `Target_Size` < `MAX_OUTPUT_SIZE` * 90% (即 0.9 * Threshold)。
    - 切分份数 `N` = `Ceil(Total_Size / Target_Size)`。
    - 实际切分点应尽量保持 Markdown 语义完整（如按行切分，避免截断多字节字符）。
4.  **文件命名**: 切分后的文件应有有序后缀，如 `_part1.md`, `_part2.md` 等。

### 2.3 边界确认
- **切分粒度**: 优先按行切分。如果单行极大（极少见），强制按字节切分可能会破坏字符编码，因此假设 Markdown 文件是基于行的文本。
- **输入源**: 适用于所有转换器生成的 Markdown 文件。
- **处理时机**: 转换完成后，写入磁盘前，或者写入后进行后处理。考虑到 `engine.py` 流程，转换通常先生成临时文件或直接写入目标路径。后处理（Post-processing）模式比较稳健。

## 3. 智能决策策略

### 3.1 决策点 1: 切分算法实现
- **方案 A**: 简单按字节切分。
    - 优点: 速度快，严格控制大小。
    - 缺点: 极易破坏 UTF-8 字符（乱码）和 Markdown 语法（如代码块被截断）。
- **方案 B**: 按行切分 (推荐)。
    - 读取文件，累加行字节数。当接近目标大小时，在行尾切分。
    - 优点: 保证字符完整，基本保证段落完整（除非段落极长且无换行）。
    - 缺点: 文件大小可能略有浮动，但可以通过设置稍小的目标值来缓冲。

**决策**: 采用 **方案 B (按行切分)**，并设置目标大小为 `Threshold * 0.9`，这留了 10% 的缓冲区，足够容纳行级误差。

### 3.2 决策点 2: 配置方式
- 在 `src/core/config.py` 中添加 `max_output_file_size` (int, default=50, unit=MB)。
- 0 表示不限制。

### 3.3 决策点 3: 命名规范
- 原文件名: `example.md`
- 切分后:
  - `example_part1.md`
  - `example_part2.md`
  - ...
- 是否保留原大文件？
  - 需求暗示是“转化时就要转化为...”，意味着替代原文件。
  - **策略**: 如果发生切分，删除（或不生成）原大文件，只保留切分后的分卷。
