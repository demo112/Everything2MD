# CONSENSUS: 文件重复校验与版本管理

## 1. 达成共识的方案

### 1.1 核心机制
- **文件指纹**: 使用 MD5 算法计算文件内容哈希，截取前 8 位作为版本标识。
- **命名规范**: `原始文件名_v{Hash}.扩展名` (例如 `report_v1234abcd.pdf`)。
- **上传策略**: Check-Delete-Rename-Upload (CDRU)。

### 1.2 详细流程
1.  **解析**: 解析本地文件名，提取基础文件名 (Basename)。
2.  **计算**: 计算本地文件内容的 Hash。
3.  **遍历**: 获取知识库中所有文件列表。
4.  **匹配**:
    - 查找知识库中是否有以 `Basename_v` 开头的文件。
    - 如果找到且 `Hash` 相同 -> **跳过** (内容未变)。
    - 如果找到且 `Hash` 不同 -> **标记删除** (旧版本)。
    - 如果未找到 -> **新文件**。
5.  **执行**:
    - 调用 RAGFlow API 批量删除标记的旧文件。
    - 将本地文件重命名为带新 Hash 的版本名。
    - 上传新文件。
    - (可选) 恢复本地文件名 (或保留版本名，视用户配置而定，当前方案为上传副本或流式上传，不修改源文件，或者上传临时重命名的文件)。**决策：上传时修改发送给服务器的文件名参数，不修改本地磁盘文件名。**

## 2. 边界条件与约束
- **API 限制**: RAGFlow 的 DELETE 接口需要支持批量删除或高并发调用。
- **文件名长度**: 增加的 `_v{8chars}` 可能会触碰某些系统的路径长度限制（但在现代 Windows/Linux 上通常不是问题）。
- **并发冲突**: 如果多个客户端同时更新同一个文件，可能会导致竞态条件（暂不考虑分布式锁，依赖 RAGFlow 自身处理）。

## 3. 验收标准
- [ ] 本地修改文件内容后，再次上传能成功上传新版本。
- [ ] 知识库中旧版本文件被自动清除。
- [ ] 知识库中文件名为 `xxx_v{hash}.ext` 格式。
- [ ] 内容未修改时，上传操作提示“跳过”。
