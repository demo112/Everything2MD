# Web界面增强 - 对齐文档 (Alignment)

## 1. 背景 (Context)
当前 Web 界面已具备基础的文件选择、配置修改和触发转换功能。但存在以下局限性：
1. **交互阻塞**: 转换过程是同步等待的，用户点击“开始”后界面卡住，直到转换完成才一次性显示日志。对于批量处理或大文件，体验极差。
2. **端口冲突**: 后端端口硬编码为 9527，可能与其他服务冲突。
3. **跨盘符导航**: 虽然后端支持，但前端交互需确认是否顺畅。
4. **功能完整性**: 需确认是否所有配置项都已暴露给前端。

## 2. 需求分析 (Requirements)
根据“进一步开发”的指令，拟定以下增强需求：

### 核心增强
- **实时日志流 (Real-time Logs)**: 使用 WebSocket 或 SSE 技术，将后端转换过程中的标准输出/错误实时推送到前端终端窗口。
- **异步任务管理**: 后端应异步执行转换任务，允许用户在转换期间进行其他操作（如取消任务）。
- **可配置端口**: 允许通过环境变量或命令行参数指定启动端口。

### 体验优化
- **增强的文件选择器**: 明确的盘符选择入口，更友好的面包屑导航。
- **配置项补全**: 检查 `config.json` 结构，确保所有有效配置均可在 Web 端修改。

## 3. 现有架构回顾
- **Backend**: FastAPI, `subprocess.run` (当前阻塞式).
- **Frontend**: 原生 HTML/JS, `fetch` API.
- **Communication**: HTTP REST API.

## 4. 关键问题 (Q&A)
- **Q: 是否需要引入数据库？**
  - A: 暂时不需要。任务是临时的，日志实时显示即可，无需持久化存储历史记录。
- **Q: WebSocket vs SSE?**
  - A: WebSocket 双向通信更灵活（例如未来支持发送“取消”指令），且 FastAPI 支持良好。选用 WebSocket。

## 5. 结论
我们将把架构从“同步等待”升级为“异步+事件驱动”，引入 WebSocket 实现实时反馈。
