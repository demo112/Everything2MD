# 需求对齐：Web端文件选择器适配

## 1. 原始需求与背景
用户在使用 Docker 运行项目时，点击网页上的“选择文件/目录”按钮，后端报错：`no display name and no $DISPLAY environment variable`。
这是因为 Docker 容器内部没有 GUI 环境，无法调用 `tkinter` 弹出宿主机的系统文件对话框。
用户建议：“文件或路径选择框用浏览器或系统的吧”。

## 2. 现状分析
- **当前实现**：后端 `/api/system/select-path` 尝试使用 `tkinter.filedialog`。这仅在本地有 GUI 环境（如 Windows 直接运行 python）时有效。
- **Docker 环境**：无 GUI，必须使用 B/S 架构的思路，即由后端提供文件列表数据，前端渲染文件选择界面。

## 3. 核心挑战
- **文件系统差异**：前端浏览器看到的是 Client 端（用户电脑）的文件，但后端 Docker 容器看到的是 Server 端（容器内部 `/work/...`）的文件。
- **交互逻辑**：用户需要选择的是**容器内挂载的路径**（如 `/work/input/file.docx`），而不是上传文件。因为 Everything2MD 的工作模式是处理本地（或挂载的）路径。

## 4. 解决方案：服务端文件浏览器
实现一个纯 Web 的文件选择器：
1.  **后端 API**：提供 `list_directory(path)` 接口，返回指定路径下的文件夹和文件列表。
2.  **前端 UI**：点击“选择”时，弹出一个 Web 模态框（Modal），显示当前目录内容。
3.  **交互**：
    - 点击文件夹：进入下一级。
    - 点击 `..`：返回上一级。
    - 点击文件/确认：将当前路径填入输入框。

## 5. 兼容性策略
- **优先策略**：为了统一体验，建议无论在 Docker 还是本地，都默认使用 **Web 文件选择器**。这样能保证 Docker 用户体验流畅，且无需配置 X11 转发等复杂操作。
- **保留选项**：原有的 `tkinter` 代码可作为遗留代码保留，或通过配置开关启用，但在 Docker 环境下自动禁用。

## 6. 待确认
- 是否允许用户浏览容器内的任意目录？（安全风险）
  - *建议限制*：默认限制在工作目录 `/work` 下，防止用户漫游到 `/etc` 等敏感目录。但考虑到是本地工具，暂不做严格限制，或者默认 `/work` 为根。
